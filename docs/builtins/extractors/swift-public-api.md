# Swift public API

This extractor captures the public API of a Swift package's library modules
directly from the compiler: every public and open declaration, its signature,
and the contract details compatibility rules inspect. Compared across a pull
request, it shows what changed in the surface your module's callers depend on.

## When to use it

Use this extractor in any Swift package that others import—a library, an SDK, or
a shared app module—when you want to review API changes as declarations instead
of digging through source diffs. New methods, removed enum cases, changed
parameter types, or classes that are no longer `open` all stand out immediately.

Because it invokes the Swift compiler (which compiles package plugins and
macros), it needs the package's Swift toolchain and `--trust`, unless you point
it at symbol graphs a build already generated. There is no built-in source-only
Swift API extractor without a toolchain; see [Build your own](#build-your-own)
if you need one.

## What it reads

By default, the extractor runs two commands in `packagePath`:

```sh
swift package dump-package
swift package dump-symbol-graph --skip-synthesized-members --minimum-access-level public --skip-inherited-docs
```

`dump-package` identifies the package's library products and their target
modules (unless you override them with `modules`). `dump-symbol-graph` then
builds the package in debug mode and emits one symbol graph per module,
including extensions on types from other modules. When `Package.resolved` is
present, SwiftPM enforces its pinned versions (`--force-resolved-versions`) and
never modifies the lockfile. Re-exported modules (`@_exported import`) have
their declarations folded in, matching what clients see.

Alternatively, set `symbolGraphPath` to a repository-relative folder of
committed `*.symbols.json` files—generated by `swift build -emit-symbol-graph`,
`xcodebuild` (using `-symbol-graph` framework builds), or
`swift-symbolgraph-extract`. Ignored or untracked files in that folder are
skipped because they aren't part of the revision. Nothing executes and no
`--trust` is needed, though every revision you compare must include those files.

```json
{
  "extractor": "swift-public-api",
  "renderer": "api",
  "inputs": {"scratchPath": ".build"},
  "execution": {"timeoutMs": 300000, "environment": ["HOME", "DEVELOPER_DIR", "TMPDIR"]}
}
```

### Time and caching

Compilation is the main cost. Here are reference timings from an Apple M-series
Mac running Swift 6.4:

<!-- prettier-ignore -->
| Package | Cold | Warm (nothing changed) | After one edit |
|---|---|---|---|
| Two modules, no dependencies | 7 s | 0.7 s | — |
| Three modules, `swift-collections` and `swift-argument-parser` | 13–20 s, plus about 2 s to resolve from SwiftPM's cache (5 s the first time, from the network) | 1.5 s | 4 s |
| A macro target on `swift-syntax` 600 | 30 s, plus 8 s to resolve from the network | 1.6 s | — |

Built-in extractors default to a 30-second `execution.timeoutMs` (up to a
300-second maximum). Small packages fit within a cold build, while larger ones
benefit from warm builds and caching:

- **Reuse build artifacts with `scratchPath`.** By default, each run builds in a
  temporary directory that is deleted afterward, so every run starts cold.
  Setting `".build"` shares SwiftPM's standard build directory: your working
  tree reuses existing builds, and persistent workspaces (using the `worktree`
  or `clone` strategy) build incrementally across revisions. (The `fresh`
  strategy always starts cold in a clean copy.)
- **Separate dependency resolution.** Resolving packages downloads them on the
  first run. Configure an environment `prepare` step running
  `swift package resolve`, keyed on `Package.resolved`, so it runs once per
  lockfile under its own timeout before extraction starts (see
  [Environments](../../runner/environments.md)).
- **Share cached extractions.** Extractions are cached per revision and
  toolchain (`environmental`), so each revision builds once—and CI can publish
  cached extractions so reviewers don't have to build locally at all.
- **Pre-generate symbol graphs in CI.** If a package is too large to build
  inline, emit the graphs in CI
  (`swift build -Xswiftc -emit-symbol-graph -Xswiftc -emit-symbol-graph-dir -Xswiftc .build/symbol-graphs`)
  and point `symbolGraphPath` at them.

## Model

Each declaration becomes an entity whose ID combines its module and Swift path
(such as `swift:Ledger.Entry.init(amount:kind:memo:)`). Because argument labels
are part of a Swift function's name, adding a parameter—even with a default
value—shows up as a new function alongside the old one's removal. Overloads that
share the same name are grouped into a single entity with multiple `signatures`.
Members added to a type from a non-re-exported module live under an extension
entity (`swift:Ledger/extension Foundation.Date.ledgerDay`).

<!-- prettier-ignore -->
| Kind | Swift | Contract facts |
|---|---|---|
| `module` | A module | — |
| `class`, `struct`, `enum`, `protocol` | Types | `sealed` (a class that isn't `open`), `supertypes` (superclass, conformances; a protocol's inherited protocols), `typeParameters` |
| `case` | Enum cases | — |
| `init`, `method`, `function`, `operator`, `subscript` | Callables | `signatures` (parameters with `default`, `variadic` and `inout` as `passing: ref`; `returns`; `typeParameters`), `static`, `abstract` (a protocol requirement without a default implementation), `optional` (`@objc optional`) |
| `property`, `variable` | Properties and globals | `type`, `readonly` (`let`, or `{ get }` only), `static` |
| `typealias`, `associatedtype` | Aliases and associated types | `type` |
| `extension` | An extension of another module's type | `type` (the extended type), `supertypes` (the conformances it adds) |

Compiler-printed attributes (`@discardableResult`, `@MainActor`) and
availability (`@available(*, deprecated, message: "…")`) are stored in
`attributes`. Swift-specific qualifiers live under `native`: `open` (members
subclasses can override), `async`, `throws`, `rethrows`, `mutating`, `final`,
`convenience`, `required`, `nonisolated`, and same-type `where` constraints. The
extraction sets `metadata.ecosystem: "swift"`, and omits implicit conformances
(`Copyable`, `Escapable`, `SendableMetatype`) and synthesized members.

## What a comparison shows

You see every added, removed, or modified declaration with its before and after
signatures. If you pair it with the
[`api-compatibility` comparator](../../../packages/comparators/api-compatibility/api-compatibility.comparator.yaml),
cross-ecosystem rules classify basic changes (removals as breaking, additions as
additive). Swift-specific rules aren't included yet, so changes like making a
class non-`open` or adding a protocol requirement appear as modifications rather
than being flagged as breaking.

## Limitations

- Builds target the host machine, so `#if os(…)` and platform availability
  follow that platform. For an iOS-only package, generate symbol graphs from an
  iOS build and load them via `symbolGraphPath`.
- Xcode projects aren't built directly; import the symbol graphs that
  `xcodebuild` emits instead.
- Doc comments, `@_spi` declarations, and `package`-level access are omitted.
- Swift-specific library evolution and resilience rules aren't applied yet—only
  generic cross-ecosystem compatibility rules run.

## Build your own

Consider writing a custom extractor if compiler symbol graphs aren't the right
fit:

- **No toolchain required**, parsing public declarations from source while
  accepting that `#if` blocks, macros, and inferred types will be approximate.
- **Platform-specific APIs**, extracting symbol graphs from an `xcodebuild` iOS
  build.
- **Extra metadata**, such as which declarations are documented, covered by
  tests, or actually used by an app.

Check the built-in options first: `modules` narrows which targets are included,
`scratchPath` enables warm builds, and `symbolGraphPath` imports graphs your CI
already generates.

**In VS Code**, open the Projections view, select **+ New Projection…**, choose
**Write a custom extractor, renderer or comparator** › **Custom extractor**, and
pick a language. You can also choose **Ask an agent to write it**.

**With the CLI**, keep the API renderer:

```sh
projections init <id> --language node --renderer api
```

Test changes as you go with `projections show -p <id> --trust`.
[Write your first extractor](../../guides/first-extractor.md) walks through a
complete example.
